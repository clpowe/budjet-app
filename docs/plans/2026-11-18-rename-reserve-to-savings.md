# Rename reserve to savings

> **Superseded in part (2026-11-18):** the table-mirroring migration, `v2` statuses and rollout steps 2–4 are dropped. Data is disposable, so see `2026-11-18-clean-schema-derived-savings-goals.md`. The wording and location table below still applies.

Use **Savings** for the household money that accumulates across budget days and funds planned Wants. Display the amount the household can use now under **Savings**. Use **from savings** in purchase breakdowns. The underlying position is signed, so an overspent household can have zero available savings and an amount to recover. The rename should preserve those distinctions and the existing calculations.

## Rollout

1. **Ship the wording.** Change “Goal reserve” to “Savings”, “Reserve used” to “Paid from savings”, and “The reserve is still syncing” to “Savings are still syncing. Try again in a moment.” A mixed purchase should read, for example, “$50 total · $30 from savings · $20 budget impact.” Update accessible labels, the glossary and copy assertions in the same change. This release can use the current API.

2. **Introduce the savings API and move its callers.** Add `api.savings.getSummary`, rename the Vue component to `WantsSavingsSummary`, and rename the internal modules to `savings_account.ts` and `want_savings.ts`. Use `summary.savings`, `availableSavingsCents`, `savingsUsedCents`, `savingsFundedCents` and `closedPositiveSavingsContributionCents`. Regenerate Convex types. Keep the old query and response fields available while existing clients use them. A status string can carry only one value: release clients that accept both `reserve_syncing` and `savings_syncing` before changing the server response, or use versioned endpoints while older clients are active. Cover both the Wants mutation’s `status` and the expense mutation’s `reason`.

3. **Migrate the three stored names.** Add `goalSavingsStates` alongside `goalReserveStates` with the same household index. Add optional `expenses.savingsUsedCents` and `dailyBudgetRollups.savingsFundedExpenseCents` alongside the old fields. Keep one authoritative source during the copy. Have all writers, including the existing money backfill, mirror updates in the same transaction. In small, rerunnable batches, copy each state by household and copy the two fields in place. Copy the exact signed position, activation time, first eligible date, last closed date and update time. Preserve absent expense funding and explicit zero. Copying must never invoke purchase, activation or day-close logic.

4. **Verify, switch, then retire the old names.** Compare state counts and each household’s position and close date, each affected expense’s funding, and each household/day rollup. Switch reads and the hourly sweep to the savings names after those comparisons match. Keep one active sweep. Let already-scheduled maintenance calls finish against the correct table and cursor, and support any queued backfill calls carrying old argument names. Retain mirrored writes through the rollback window. Once old clients and jobs have drained, stop mirroring, remove legacy fields in batches, retire the old table and compatibility endpoints, and restore the required validator on the new rollup field.

## Acceptance checks

- Compare Home and Wants summaries for the same household and timestamp before and after migration. Check positive savings, a negative position, and a household that has never activated savings.
- Exercise a partially savings-funded purchase, its correction and undo, and a retry while days are closing. Confirm the expense total equals savings used plus budget impact and each day closes exactly once.
- Re-run the migration against already-copied rows and exercise a purchase during the copy. Verify balances, allocations, expense IDs and rollups still match.
- Run `vp check` and `vp test`. Search product source, filenames and the glossary for remaining uses of “reserve”, including camel-case identifiers and `RESERVE_SYNCING`. Review intentional compatibility and migration references separately from unrelated words such as “preserve”.

## Deployment

Deploy the compatibility backend before the new frontend. Run `pnpm exec convex run migrations/renameSavings:start '{}'` against the intended deployment. The mutation schedules the copy and returns immediately. The migration verifies both state tables, expense funding, and rollups, then writes a single `savingsMigration.verifiedAt` marker. Check that marker and scheduled job errors before treating the migration as complete. A mismatch stops the job before cutover. After reconciling it, run the same command again.

Fresh hourly sweeps use the savings table after verification. In-flight sweeps retain their source table with their cursor. Both sets of fields and tables stay in sync during the compatibility window. The frontend requests version 2 retry responses. Older clients can continue to use the original status and query. Schedule removal of the legacy names after those clients and queued jobs retire.
